# Решение

## 1. Что сделано

### Скидки в статистике (`GET /customers/:id/daily-totals`)

Ответ стал `[{ date, total, gross, discount, net }]`; `total` сохранён и равен `gross`.

| Файл | Что изменилось |
|---|---|
| `migrations/002_order_discount.sql` | `orders.amount_paid_kop BIGINT` (nullable) |
| `src/services/orders.ts` | в схеме появился `amountPaid` (число **или** строка); `discountPercent` не разбираем — см. «Допущения» |
| `src/repositories/orders.ts` | поле `amountPaidKop: number \| null` в модели и в записи/чтении |
| `src/services/totals.ts` | посуточно копятся `gross` и `net` в копейках; `discount = gross - net`; ответ через `fromKop` |
| `src/utils/money.ts` | `toKop` больше не теряет копейку (см. п. 3) |

Суммы складываются в копейках (`bigint`), как и было принято в сервисе: `discount` — разность целых копеек, а не пересчёт процентов в float. Дни без оплат остаются с нулями, `pending`/`refunded` не учитываются — как до изменений.

### Исправление расхождения из жалобы

| Файл | Что изменилось |
|---|---|
| `src/utils/time.ts` | вместо `tzOffsetMinutes` + `dateAtOffset` — `localDate(at, timeZone)`: календарный день момента получается через `Intl.DateTimeFormat` **по самому моменту**; форматтер кэшируется на таймзону |
| `src/services/totals.ts` | убран `tzOffsetMinutes(timezone, new Date())` — каждый заказ группируется по собственному моменту |

## 2. Причина расхождения и как она найдена

**Причина — переход на летнее время, на который сервис накладывает одно смещение, посчитанное по «сейчас».**

`src/services/totals.ts` до правки считал смещение таймзоны клиента один раз на момент запроса и применял его ко всем заказам периода:

```ts
const offset = tzOffsetMinutes(timezone, new Date());   // ← «сейчас»
const date = dateAtOffset(o.createdAt, offset);         // ← для заказа полугодичной давности
```

Клиент `c_7` — `Europe/Berlin` (проверено: `GET /customers/c_7`). В 2026 году переход на летнее время в Берлине — **29 марта, 01:00 UTC**: до `+01:00`, после `+02:00`. Окно жалобы `27–31.03` как раз пересекает границу.

Последствия (смещение сегодня, в ноябре, = `+01:00`):

- `27.03` и `28.03` — смещение угадано верно, суммы сходятся до копейки;
- заказы, оплаченные в последний час перед локальной полуночью **после** перехода, уезжают на сутки назад: `2026-03-29T22:40:08Z` — это берлинские `30.03 00:40`, а сервис относил их к `29.03`.

Отсюда и формулировка аналитиков: часть дней расходится, часть совпадает идеально. Соседний симптом: заказ `2026-03-31T22:40:06Z` (берлинское `01.04 00:40`) прибивалось к `31.03`, то есть последний день отчёта получал чужие деньги.

Побочное следствие, важное для воспроизводимости: ответ зависел **от даты, в которую его запросили**. Один и тот же запрос в июле и в ноябре давал разные суммы, потому что менялось «сейчас».

**Как искали.** Жалоба описывает расхождение по дням, поэтому начали с границы суток, а не с денег: прочитали `daily()` → увидели `new Date()` → проверили на живом клиенте. Шаги:

1. `curl /customers/c_7` → `Europe/Berlin`;
2. перебором посекундно нашли момент перехода — `2026-03-29T01:00Z`, `+60 → +120` мин;
3. выгрузили все 5030 заказов внешнего API и для каждого сравнили «верный» берлинский день с тем, что даёт формула сервиса: разошлись ровно `29.03`, `30.03`, `31.03`, а `27.03`–`28.03` совпали до копейки;
4. в расхождении участвовал один оплаченный заказ в сутки — `o_02357`, `o_02448`, `o_02547` (все локализованы в `00:15–00:40` по Берлину).

## 3. Что ещё заметили

1. **`toKop` терял копейку на реальных суммах.** Было `Math.floor(rub * 100)`, а `4549.23 * 100 = 454922.99999999994` → `454922`. На выборке внешнего API так теряют копейку **96 заказов**, причём `amount` (целые рубли) не ломался никогда — баг спал, пока не появились дробные `amountPaid`. Прямо внутри окна жалобы это `28.03` (−2 коп.), `29.03` и `31.03` (по −1 коп.): если бы `net` посчитали прежним `toKop`, «скидки» сами внесли бы расхождение в копейки как раз в те дни, которые раньше совпадали. Исправлено на точный разбор десятичной записи; поведение «доли копейки отбрасываются» сохранено (`toKop(10.999) === 1099`), поэтому прежний тест остался зелёным.
2. **Вебхуки теряют более свежие версии заказа (гонка).** `OrdersService.apply` делал «прочитать текущий заказ → сравнить в памяти → записать», а внешняя система раздаёт вебхуки параллельно. Две доставки одного заказа успевают прочитать одно и то же состояние, и побеждает та, что позже записала, а не та, что новее по `updatedAt`. В живом прогоне это стоило 1357.92 ₽ на `30.03`: заказ `o_02362` в базе остался в версии `5313.60 @02:15`, хотя позже пришла и должна была победить версия `3955.68 @03:15`; `o_02559` вместо `refunded @04:53` остался `paid @03:53` (то есть деньги вернулись в отчёт). Доказательство A/B: те же 92 вебхука, доставленные **последовательно**, дают корректное состояние, а доставленные так, как их шлёт мок, — нет. Исправлено атомарно: сравнение и запись одним `INSERT ... ON CONFLICT DO UPDATE ... WHERE orders.updated_at < excluded.updated_at`. Без этого `result.json` был бы невоспроизводим.
3. **Поля скидки появились у API 15.03.2026, и до этой даты их нет у 1177 заказов из 5030** — как пары `discountPercent` + `amountPaid`. Отдельного «процент без суммы» в выборке нет (0 случаев), поэтому `net` считаем строго по `amountPaid`.
4. **`discountPercent` приходит и числом, и строкой** (177 строк вида `"33"` на 3853 заказа со скидкой), `amount` — строкой в 157 случаях, `createdAt` без указателя зоны — в 288 случаях из 5030 (в вебхуках — 45 из 92). Для `amount` и дат это уже обрабатывалось; разбор нового поля унаследовал тот же толерантный путь.
5. **`amountPaid` всегда согласован с `amount × (1 − discountPercent/100)`**: 0 расхождений больше копейки на 3853 заказах. Отсюда решение не хранить процент: он не несёт информации, которой нет в `amount` и `amountPaid`.
6. **Внешний API подтвердил обе «странности» из комментариев в коде**: за 52 страницы дважды прилетело `200 {"error":"rate_limited"}` вместо 429, а заканчивается выдача пустой страницей с тем же курсором. Ретраи клиента с этим справляются (синк: `{"pages":52,"received":5030,"applied":5030,"invalid":0}`).
7. **`refunded` исчезает из статистики целиком**, а не уходит в минус: оплаченный и затем возвращённый заказ убирает свою сумму из того дня, в котором он был оплачен. Для `29.03` это −14907 ₽ относительно «до вебхуков». Поступление платёжной системы (возврат надо бы показывать отдельной строкой или в день возврата) в задании не описано, поэтому поведение оставил как есть.
8. Мелочи: `sync_runs` не хранит `applied`/`stale`/`invalid`, хотя `SyncStats` их считает, а `HttpOrdersApi` при `429` без `Retry-After` не делает паузы на backoff (в отличие от 5xx). На суммы не влияют.

## 4. Допущения (там, где требования неоднозначны)

- **`net` = `amountPaid`** (факт списания платёжной системой), `discount = gross − net`, а не пересчёт из `discountPercent`. Пункт 2 жалобы сверяется с отчётом платёжной системы, значит истина в списанной сумме; согласованность процентов с суммами проверена на всех 3853 заказах (п. 3.5).
- **Нет `amountPaid` → `net = gross`, `discount = 0`.** Так ведут себя заказы до 15.03.2026: скидку мы не выдумываем и не приносим из процентов. В колонке это `NULL`, а не `0`.
- **`discountPercent` в сервис не сохраняется.** Он не нужен ни для `net`, ни для `discount`, а лишнее поле в БД и в модели заказа кому-то потом поддерживать.
- **`total` = `gross`** (по заданию), то есть в отчёте по-прежнему «сумма до скидок», и `pending`/`refunded` не участвуют ни в одной из трёх сумм.
- **`result.json` кладу в корень `orders-aggregator`**, а `from`/`to` трактую включительно (оба крайних дня входят) — как и до правки.
- **Таймзону для группировки берём по моменту заказа (`createdAt`)**, потому что `paidCreatedBetween` и весь отчёт привязаны к дате создания; отдельного момента списания внешний API не отдаёт.
- **Существующие тесты `test/totals.test.ts` обновлены**, а не обойдены: они сверяли ответ через `toEqual` по точной форме `{ date, total }`, а контракт изменился по требованию задания — с новыми полями эти утверждения падают в любом случае. Изменены только ожидаемые формы объектов, логика кейсов та же (в комментарии к задаче есть отдельный пункт про то, как проверяли).

## 5. Что доделал бы при наличии времени

- **Возвраты**: отдельная метрика (например, `refunded` и/или `net` со знаком в день возврата) и сверка с платёжной системой, потому что «исчезновение» денег из дня оплаты — это то, что аналитики заметят следующим.
- **Тест на контракте ответа**: схема ответа (Zod-валидация outgoing или snapshot-тест), чтобы добавление полей не ломало потребителей молча.
- **Группировку в базе**: `daily()` считает сутки по заказам, но окно выборки (`-1 сутки … +2 сутки`) оправдано только текущим ±14 ч; при росте объёмов лучше отдавать группировку в SQL (`date_trunc` с `AT TIME ZONE`) и не вытаскивать заказы в память.
- **Идемпотентность вебхуков по `eventId`** вместо сравнения `updatedAt`: сейчас два разных события с одинаковым `updatedAt` (например, правка суммы без изменения времени) приводят к потере второго.
- **`sync_runs`**: дописать `applied`/`stale`/`invalid` в таблицу — статистика уже считается и теряется.

## 6. Как проверяли результат

1. **Тесты**: `npm test` → **39 passed** (было 27). Добавлены: `toKop` против потери копейки, `localDate` через границу перехода, короткие сутки перехода, четыре кейса на скидки в `daily-totals`, регрессия на сутки перехода на уровне HTTP-ручки (заказ не уезжает в предыдущий день + заказ локального утра последнего дня не попадает в отчёт), кейсы `amountPaid` для `/sync` и `/webhooks/order`, тест на параллельную доставку версий.
2. **Тесты действительно ловят баги** (иначе они не доказательства). Две проверки сделаны «обратным прогоном»:
   - временно вернули `tzOffsetMinutes(timezone, new Date())` → `test/totals.test.ts`: **2 failed | 10 passed** (`RED_EXIT=1`), остальные кейсы зелёные;
   - временно вернули «прочитал → сравнил → записал» → `test/webhooks.test.ts`: **1 failed | 6 passed**, падает уже на первом раунде (`осталась устаревшая версия: expected 1000 to be 2000`).
   После возврата исправлений — `typecheck` exit 0 и все 39 тестов зелёные.
3. **Независимый пересчёт.** Ответ сервиса сравнен с расчётом, который не использует код сервиса: снимок всех 5030 заказов внешнего API + наложение 92 записанных вебхуков по правилу «побеждает строго более свежая версия» → посуточные суммы в копейках → сравнение с `result.json`. Итог: **0 расхождений поштучно на 64 оплаченных заказах окна, все 5 дней совпали до копейки**. (Первая версия этого сверочного скрипта сама была сломана — неверно считала смещение и давала расхождение на пяти днях из пяти; это ловится тем, что расхождение оказалось в *проверке*, а не в сервисе: последовательная доставка тех же вебхуков показала корректное состояние БД.)
4. **Воспроизводимость `result.json`**: процедура прогнана дважды подряд с нуля — ответы побайтово идентичны (`diff` пустой). До исправления гонки это не так: результат зависел от того, какая из параллельных доставок запишется последней.
5. **Ручная проверка API**: `POST /sync` → `{"pages":52,"received":5030,"applied":5030,"stale":0,"invalid":0}`; `webhooks sent: 92, responses: {"200":92}`; `GET /health` → `{"status":"ok"}`; невалидное тело вебхука → `400 {"error":"bad_request",...}`.

### Как получить `result.json`

```bash
docker load -i ../orders-mock-arm64.tar.gz        # или amd64
cp .env.example .env
docker compose up -d                              # postgres + orders-api
npm install
npm run migrate                                   # применятся 001 и 002

docker exec orders-aggregator-postgres-1 psql -U postgres -d orders -q \
  -c 'DROP SCHEMA public CASCADE; CREATE SCHEMA public;'   # чистая БД
npm run migrate
npm run start                                     # http://localhost:3000
curl -X POST http://localhost:3000/sync           # дождаться (52 страницы, ~15 с)
docker compose run --rm orders-api webhooks \
  --target http://host.docker.internal:3000/webhooks/order   # 92 вебхука
curl "http://localhost:3000/customers/c_7/daily-totals?from=2026-03-27&to=2026-03-31"
```

`result.json` — тело последнего запроса дословно (файл побайтово равен ответу сервиса). Процедура прогнана трижды: дважды подряд через локальный логгер, который пересылал вебхуки сервису без изменений (нужно было разобрать состав доставок — см. п. 3.2), и один раз ровно командой из `README.md` с прямым адресом сервиса; все три ответа совпали побайтово.
